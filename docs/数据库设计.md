# 数据库设计（MySQL 8.0）

## 1. 设计目标

原版把整份数据塞进一个 JSON（`{managers[], plans[], visits[]}`），存在浏览器 localStorage 或 Supabase 的单行
`payload` 里。这样带来三个问题：换设备看不到、多人同时写互相覆盖、集团与月份字段冗余且易不一致。

新版按关系模型拆成 4 张表，保证：

- 账号与身份由数据库维护，可停用、可重置密码
- 集团只维护一份（编码唯一），计划引用集团
- 计划由「客户经理 + 集团 + 月份」唯一确定，重复分配直接拦截
- 一条计划最多一条拜访记录（DB 唯一约束，业务层再校验一次）
- 删除动作有明确级联路径，不残留孤儿数据

## 2. ER 关系

```
sys_user (1) ──< visit_plan >── (1) customer_group
                    │
                    └──(0..1) visit_record
```

- 一位客户经理可以有多条计划；一个集团可以出现在多位经理的计划里
- 一条计划对应 0 或 1 条拜访记录
- 删除客户经理 / 集团会级联删除相关计划；删除计划级联删除拜访记录

## 3. 表结构

### 3.1 sys_user（账号）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT PK AI | 主键 |
| username | VARCHAR(50) UK | 登录账号 |
| real_name | VARCHAR(50) | 姓名（列表展示、导入匹配） |
| password | VARCHAR(100) | BCrypt 哈希 |
| role | VARCHAR(20) | `ADMIN` / `MANAGER` |
| enabled | TINYINT | 1 启用 / 0 停用 |
| created_at / updated_at | DATETIME | 时间戳 |

索引：`uk_user_username(username)`、`idx_user_role(role, enabled)`

### 3.2 customer_group（集团主数据）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT PK AI | |
| code | VARCHAR(30) UK | 集团编码 |
| name | VARCHAR(120) | 集团名称 |
| created_at / updated_at | DATETIME | |

索引：`uk_group_code(code)`、`idx_group_name(name)`

### 3.3 visit_plan（拜访计划）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT PK AI | |
| manager_id | BIGINT FK → sys_user.id | 客户经理 |
| group_id | BIGINT FK → customer_group.id | 集团 |
| plan_month | CHAR(7) | `YYYY-MM` |
| remark | VARCHAR(255) | 备注 |
| created_at / updated_at | DATETIME | |

索引与约束：

- `uk_plan(manager_id, group_id, plan_month)`：同一经理同一集团同月只能有一条计划
- `idx_plan_month(plan_month)`：按月份筛选/统计
- `idx_plan_group(group_id)`：集团被引用数、按集团统计
- 外键 `ON DELETE CASCADE`（删除经理/集团时清理计划）

### 3.4 visit_record（拜访记录）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT PK AI | |
| plan_id | BIGINT FK → visit_plan.id | 计划 |
| visit_date | DATE | 实际拜访日期 |
| method | VARCHAR(20) | 拜访方式（受控枚举） |
| result | VARCHAR(30) | 拜访结果（受控枚举） |
| remark | VARCHAR(1000) | 拜访记录 |
| created_by | BIGINT | 提交人（管理者代登记时与计划归属可能不同） |
| created_at / updated_at | DATETIME | |

索引与约束：

- `uk_record_plan(plan_id)`：一条计划最多一条记录（关键约束）
- `idx_record_date(visit_date)`：按日期导出/统计
- `ON DELETE CASCADE`：计划删除时记录同步删除

## 4. 关键取舍

**月份用 CHAR(7) 而不是 DATE**
原版只有「十月/十一月/十二月」三个键，无法跨年。改为 `YYYY-MM` 字符串：
- 排序、比较都是字典序，天然正确
- 不需要关心"当月第几天"，避免时区/月末问题
- 与 Excel 表头（`2026-10`）直接对应，导入导出无需转换

**集团独立成表**
原版每个「客户经理-集团-月份」都带一份 `name`，改名要遍历所有记录。独立后集团编码唯一，
导入时若表格里的名称与库中不一致，保留库中名称并给出警告，避免静默改名。

**不用 ORM，直接 JdbcTemplate + 手写 SQL**
统计需要多次聚合（`COUNT(DISTINCT)`, `GROUP_CONCAT`, `LAST_DAY(STR_TO_DATE(...))`），
手写 SQL 更直观，也不用处理实体映射与懒加载问题；同时把依赖压到最小。

**删除的语义**
删除客户经理/集团属于"结构性删除"，用外键级联一次清理；业务上由前端二次确认并提示影响条数。
导入的「按范围替换」只在「涉及的经理 + 月份」范围内删除，避免误清全库。

**索引选择的依据**
主查询是「按经理/月份/状态筛选 + 集团名称关键字」：
- `(manager_id, group_id, plan_month)` 唯一索引覆盖经理维度
- `plan_month` 单列索引覆盖月份筛选与月度统计
- 集团名称 `LIKE '%xxx%'` 无法走索引，数据量大时可改用前缀匹配或全文索引

## 5. 初始化数据

- `backend/db/schema.sql`：纯表结构（`docker-entrypoint-initdb.d` 直接可用）
- 首次启动由 `DataInitializer` 写入：
  - 管理者 `admin / admin123`
  - 3 位客户经理（xiaoli / xiaogan / xiaoguo，密码 123456）
  - 10 家集团（G001~G010）
  - 每人 10 条计划（分布在当前月及后两个月）
  - 4 条当月拜访记录（保证统计页有数据）
- 关闭演示数据：环境变量 `INIT_DEMO=false`（只建 admin）
